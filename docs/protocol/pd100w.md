# Maono PD100W vendor HID protocol map

Read-only research, 2026-10-07. Every hardware check used GET (type 0x04) only. No SET was sent.

## 1. Source and method

- **App:** Maono Link **3.8.52**, the macOS build. Downloaded from
  `https://update.maono.com/uploads/202609/Maono%20Link_V3.8.52.pkg` (571 MB, Last-Modified 2026-09-24).
  The download page also lists Windows `Maono Link_V4.0.88_0918.exe` and the older mac `Maono Link_V3.6.9.pkg`.
- **Extraction:** `bsdtar` on the xar pkg, then `gzip -dc Payload | cpio` for `MaonoLinkApp.pkg`.
- **Device library:** `Maono Link.app/Contents/Frameworks/libPD100XW.dylib` (x86_64 + arm64 fat binary, 25.9 MB, built 2026-09-23).
  - `Resources/MaonoDevicesInfo.txt` routes PIDs to it:
    - `0417` PD100W_USB (wired mic, our case)
    - `0414` PD100W_RX
    - `0416` PD100W_CRX
    - `0415` PD100W_lightning
  - The UI class it uses is `View_Total_PD200X`. PD100W and PD200W share the same "PD200XW" DSP platform, and the device's own string at 0x0003 reads `PD200XW`.
- **Tooling** (no installs): `llvm-nm`, `llvm-objdump` (x86_64 slice), plus small Python helpers for cstrings, constants and jump tables.
- **Where things came from:**
  - The id→enum table is from `Analyzer::switch_analyzer`, which holds 110 `BidirectionalMap<short,MessageType>::insert` calls.
  - Enum meanings come from UI lambdas (`View_Total_PD200X::createBasicWidget/createLightWidget/createSceneWidget/createMornitorOutputWidget`), matched to their labels by connect order.
  - Encodings come from `Analyzer::slot_FromUI`, `GetActual*/GetUIParam*`, `DataCenter_100w::AudioEQ_ProcessSinglePoint` and the `Process*` handlers.
- **Not used:** `MacOS/Original.equ` (base64 plus a 12-byte XOR) was not needed, because the presets are stored as plaintext JSON in the dylib cstrings.
- Scratch artifacts are in `scratchpad/maono-link/`:
  - `scan_*.txt` (one level up)
  - `dis_x86.txt`, `cstring_pd100xw.txt`, `mt_xref.txt`, `stubs.txt`

## 2. Frame formats (confirmed in `DataPackage::*`)

Every frame is prefixed by HID report id 0. The app writes a 64-byte buffer: byte 0 = 0x00, followed by the frame. `ck` = `-(sum of all preceding frame bytes) & 0xFFFF`, little-endian.

| Type | Builder | Layout | Notes |
|---|---|---|---|
| 0x03 SET | `PackageRandomMessage(id, short val)` | `c4 0b 00 00 03 idL idH vL vH ckL ckH` | value is a **signed short** |
| 0x03 multi-SET | `PackageRandomMessageQMap / QVector(ids, vals)` | `c4 (4n+7) 00 00 03 [idL idH vL vH]×n ck` | the EQ band write uses this (5 pairs per band) |
| 0x04 GET | `PackageRandomMessage(id)` | `c4 09 00 00 04 idL idH ckL ckH` | the app sends a 9-byte GET; `maono` sends len 0x0b with val 0 and the device accepts that too |
| 0x04 multi-GET | `PackageRandomMessageQVector(QList<ushort>)` | `c4 (2n+7) 00 00 04 [idL idH]×n ck` | the init fetch uses this |
| 0x05 range write | `PackageContinuousMessage(start, count, QList<short>)` | `c4 (2n+11) 00 00 05 startL startH cntL cntH [vL vH]×n ck` | used by `WriteSNCode` (SN padded with 0xFEFE). `slot_FromUI` also uses it when the keys being written are consecutive (`isConsecutiveKeys`) |
| 0x06 range read | `PackagereadContinuousMessage(start, count)` | `c4 0b 00 00 06 startL startH cntL cntH ck` | the reply has type 0x06 (`AnalyseContinuousRead` → `Sig_ContinuousRead(start, QList)`). Used for SN (0x1e×16, 0x2e×16), compressor block (0x2069×10) and custom colours (0x208f×3N) |

Receive side (`AnalyseDatas`):
- 0x03 is a change notification (11-byte frames, which is how button presses arrive).
- 0x04 is a read reply.
- 0x06 is a range-read reply.
- `SplitCoalescingPacket` splits several frames concatenated in one report.

Value conversions in `Analyzer::slot_FromUI` and the Analyzer UI decoders:
- `GetActual(x) = x*100`, used for Q and the custom-colour HSV ids.
- `GetActual2(dB) = dB*10 + 2000`, used for EQ gain and the compressor/limiter thresholds (0x206a, 0x206f).
- The reverse conversions are `GetUIParam = raw/100` and `GetUIParam2 = (raw-2000)/10`.

## 3. Slot layout

All feature ids are relative to a slot base: **0x2000 = TX1 / wired mic**, **0x2800 = TX2**, **0x3000 = receiver**. The receiver map is different; see §4.4.

In wired mode (PID 0417), 0x3000–0x3094 all read 0, and 0x2800 is unused.

## 4. Field table

**Confidence key:**
- **C** = the meaning comes from the binary, and the value read back from the device is plausible for it. **Nothing was confirmed by watching a value change after a write**, because SET was off-limits. For mute, gain, NR and light, the README already had change-based confirmation.
- **B** = from the binary only (the device answers, but the meaning comes from code).
- **G** = guessed.
- **?** = the device answers but no meaning was found.

`MT` is the app's internal `MessageType` enum. "Current" means read on 2026-10-07, mic wired. All ids in the 0x20xx blocks have TX2 twins at +0x800.

### 4.2 Compressor and limiter

These are in `createBasicWidget`'s "More" dialogs. The range constants are double arrays at 0xaa650/0xaa6c8.

| Id | MT | Feature | Range / encoding | Current | Conf |
|---|---|---|---|---|---|
| 0x2069 | 71 | Compressor on/off | 0/1 | 0 | B |
| 0x206A | 72 | Comp threshold | −48..0 dB, raw = dB×10+2000 | 1800 (−20 dB) | B |
| 0x206B | 73 | Comp attack | 0..400 ms, raw = ms | 20 | B |
| 0x206C | 74 | Comp release | 0..2000 ms, raw = ms | 800 | B |
| 0x206D | 75 | Comp ratio | 1..12 (N:1), raw = N | 2 | B |

| 0x2070 | 78 | Limiter attack | 5..400 ms | 0 (below UI min) | B |

| 0x2072 | 80 | ? read in the same 10-id block, not used by the UI | | 1 | ? |

How the UI order maps to ids:
- Compressor: UI order is threshold, ratio, attack, release. The lambda's jump table maps them to 72, 75, 73, 74.
- Limiter: UI order is threshold, attack, release, mapping to 77, 78, 79.
- The whole block is read with one range read: `06` 0x2069, count 10.

A code path in `createBasicWidget` logs "MAONO 创建UI 压缩器隐藏" ("compressor hidden") and hides two widgets. The comp/limiter panel may therefore not be visible in every app state or version. The device answers these ids regardless.

What "applying a scene" means:
- The app writes the 7 EQ slots: one multi-SET of 5 pairs per slot.

## 6. Things that are not a simple id/value pair

- **Multi-pair SET (type 0x03)** for the EQ: each band is one frame with 5 pairs.
- **Range write (0x05) and range read (0x06)**:
  - Serial number write (`WriteSNCode`: 0x1E or 0x2E, 16 words; dangerous).
  - Compressor block read (0x2069×10).
  - Custom colour read (0x208F×3N).
  - The app also uses 0x05 automatically whenever a UI write touches consecutive ids.
  - 0x06 is a read, but it was **not sent** in this research (GET-only rule).
- **Factory reset:** `FactoryRecoveryCommand` = **SET 0x100A = 3**. This is the only id seen in a 0x1000 slot. It also resets the app's local scene config. **Never send.**
- **Host-app flag:** SET 0x20B4 = 1/0 on app open/close.
- **No explicit save/commit command exists** in `libPD100XW`. Values are written directly. Persistence across power cycles was not tested. The app UI notes that turning the indicator LED off is undone on disconnect or restart, which suggests at least some fields are volatile.
- **Firmware update** lives in `libmaonofirmware.dylib`, which is arm64-only:
  - Generic `maonoFirmwareDll`.
  - Downloads from the Maono server (`firmwareDownloadUrl`).
  - Pushes data through the same HID channel (`hid_UIsend_data`/`receiveHIDdata`).
  - The flashing protocol was not analysed. Out of scope and dangerous.
- **Scenes and curves are app-side:** names, custom curves and import/export `.cfg`/`.equ` files are local. The device only stores the 7 active EQ slots, the reverb settings and the 0x2022 bookkeeping word.
- **AI noise reduction** ("Maono AI Microphone", `MaonoAIService.pkg`) is host-side processing. It is not a device field, apart from forcing the monitor code to 2 (computer only), or 7 when it is off.
- **Voice changer / tone:** no such field or UI exists in `libPD100XW`. Reverb is the only effect.
- **Mute LED:** there is no separate field. The red ring follows 0x207D.
- **Auto power-off:** no field was identified. 0x2086=40 is an unverified candidate.

## 7. Open questions

1. Meanings of 0x2081, 0x2086 (=40), 0x2087, 0x2088, 0x208D and 0x2072. They answer GET but no UI references them. The same is true in the PD200XW lib.
2. Reverb level base. The int is passed raw from the option group, inferred 0..9 = UI 1..10. Current value is 1. Confirm by watching notifications while changing it in the vendor app, or with a single SET.
3. EQ `blnBypass`. The single-point writer always sets enable=1, so it is not clear how the app bypasses LPF/HPF (Pop's LPF). Writing enable=0 at slot+0 may work, but this is untested.
4. EQ gain range. The app clamps anything below −12 dB to 0 dB (raw 2000), which implies a usable range of about ±12 dB. The upper bound was not found.
5. Custom colours.
   - What colour code 8 shows when 0x208E=0 (the README saw "light blue")?
   - Does the device accept H > 32767 (signed-short overflow)?
6. 0x0045 polarity (mute versus enable of the level stream). The "sleepSwitch" naming is confusing.
7. Persistence of settings across power-off, and whether 0x20B4 changes device behaviour (for example, disabling the on-mic buttons).
8. Second EQ block 0x2046–0x2068. It is assumed to be factory voicing. Treat it as read-only.
9. Limiter attack/release read 0, below the UI minimum of 5. They are possibly unused by the firmware.

de 76 ids mapeados. Al final se restauró todo y se comprobó que no quedaba ninguna diferencia.
Solo se escribieron ids de la allowlist, dentro de los rangos de la app. No se tocaron 0x100A,
la serie ni 0x2046–0x2068. 0x20B4 se usó una vez (1 y luego 0), igual que la app al abrirse y cerrarse.
